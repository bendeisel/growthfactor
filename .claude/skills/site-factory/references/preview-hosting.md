# Preview hosting

The goal: hand a client a real URL of their own site, on our domain, before
they have paid for or pointed a domain at anything — and keep that URL working
and distinguishable after the real site launches.

## The shape

```
preview.<gf-domain>/<slug>/          <- what the client gets sent
        │                  │
        │                  └─ one directory per client build
        └─ ONE Hostinger subdomain, created once, pointed at previews/
```

On disk, inside the preview website's `public_html`:

```
public_html/
├── previews/
│   ├── spidersboxing/     index.html, programs.html, style.css, img/, robots.txt
│   ├── fighters/
│   └── nashvillemma/
└── index.html             a plain index, or a 403 — never a directory listing
```

Created once, with `hostinger.sh subdomain-add`:

```
POST .../subdomains  {"subdomain":"preview","directory":"previews","is_using_public_directory":false}
```

Per-client previews are **directories, not subdomains**. A subdomain per
prospect means a DNS record and an SSL cert per prospect, for people who have
not signed yet. Directories cost nothing and give the path-per-business scheme
the routines assume: `/spidersboxing`, `/fighters`.

## The hazard that shapes all of this

`POST /api/hosting/v1/accounts/{username}/websites/{domain}/deploy` **replaces
the entire contents of a website.** Not a directory — the website.

So:

- **The preview host is its own Hostinger website**, on a domain that hosts
  nothing else. Not a directory inside the agency's marketing site, and never
  inside a client's site.
- **Never call `deploy` against the preview website.** One call would delete
  every client preview at once. `deploy_preview.sh` uploads files individually
  over TUS and has no code path that can reach the deploy endpoint;
  `deploy_production.sh` refuses to run when the target domain matches the
  configured preview domain. Both guards are load-bearing — do not remove them
  to save a step.

## Slugs

The slug is the client's identity across the whole system: the preview path,
the registry key, the project directory, the artifact title. Pick it once at
intake and never change it.

- lowercase, `a-z0-9-` only, no leading or trailing dash
- the business name, not the vertical: `spidersboxing`, not `boxing`
- collapse spaces and drop punctuation: "Spider's Boxing & Fitness" →
  `spidersboxing`
- on collision with an existing registry row, append the city: `fighters-nash`

`registry.py` validates the slug and rejects a duplicate rather than
overwriting a row, because the failure it prevents is quietly replacing one
client's preview with another's.

## Previews are noindex, always

A preview is a byte-identical copy of a client's site on a domain we own. Left
open, it is duplicate content competing with the client's real site, and
Google will index a preview subdomain nobody linked to.

`deploy_preview.sh` writes both belts:

- `previews/<slug>/robots.txt` — `User-agent: * / Disallow: /`
- `<meta name="robots" content="noindex,nofollow">` injected into every page

Neither is decoration. Removing them creates an SEO problem on the client's
production site that outlives the preview.

## Telling previews apart without opening them

Three layers, so the question "which build is this?" never needs a browser:

1. **The registry** (`data/sites.csv`) — one row per build: client, slug,
   vertical, city, artifact URL, preview URL, production domain, status, dates.
   `python3 scripts/registry.py list --status preview` answers it from a
   terminal.
2. **The `<title>`** of every preview page carries the client name, so browser
   tabs and history are readable.
3. **The preview badge** — a small fixed marker the shell renders when it is
   running as a preview, showing client and slug. It is inside the chrome
   markers, so `split_pages.py` strips it and it never ships.

## After production launch, the preview stays

The client's site going live does not retire the preview URL. Because
production is a different website, launching touches nothing under
`previews/`, and the row keeps both URLs with `status=live`.

That is what makes the preview path the stable address for a build: it is the
one URL that exists from first draft to after launch.

## Where editing actually happens

The preview and the production site are **outputs**. Neither is an editing
surface.

```
projects/<slug>/          source of truth, in git
      │
      ├──> artifact       the review surface (client and internal review)
      ├──> preview        generated by deploy_preview.sh
      └──> production     generated by deploy_production.sh
```

Do not hand-edit files on Hostinger. A production deploy overwrites the whole
website, so server-side edits are destroyed without warning on the next ship,
and nothing in git would show what was lost. Change the source, re-run the
routine — which takes about as long as the edit would have.
